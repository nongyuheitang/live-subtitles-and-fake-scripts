# 后续优化建议

## 优先级概览

| 优先级 | 项目 | 目标 |
| --- | --- | --- |
| P0 | 自动预检与发布打包 | 防止占位符、敏感信息、丢失资产进入正式包 |
| P1 | 干净成功录制 | 公开展示中不再出现原始探索失败 |
| P1 | 自然语言改名状态机 | 生成后可安全改名并同步 artifact |
| P1 | Topic Naming 兼容 | 主回放结束后不再产生辅助请求告警 |
| P1 | 自动资产生成管线 | 生成、检查、存档和回放资产一次完成 |
| P2 | 一键启动与健康检查 | 降低现场配置步骤和人为错误 |
| P2 | 可视化剧本编辑器 | 非研发人员也能调整文字、时长和资产 |

## 1. P0：增加 `validate` 与 `package` 命令

目前正式包仍需要人工完成多项检查。建议新增：

```text
node replay-cli.mjs validate examples/ppt-demo
node replay-cli.mjs package examples/ppt-demo --out dist/
```

`validate` 至少检查：

1. 所有 JSON 可以解析并符合 schema。
2. `turns` 数量与预期一致。
3. 每个带 result 的 tool call 都能唯一匹配。
4. `report_artifacts` 引用的文件一定存在。
5. `{{OUTPUT_DIR}}` 和 `{{SCRIPT_DIR}}` 只出现在允许展开的位置。
6. 二进制资产存在、非零且 SHA-256 一致。
7. PPTX 可解压，slide 数量符合声明。
8. PDF 页数、页面尺寸和文本提取符合声明。
9. `sleep N && <命令>` 直接判为错误。
10. `node_modules`、`.state`、日志和输出目录不会进入包。
11. 扫描 API Key、Cookie、密码、真实服务器地址和用户目录绝对路径。
12. 最终正文中的文件名、大小、页数与真实资产一致。

`package` 应只复制 allowlist 文件，然后自动生成校验清单和解压验证报告。

## 2. P1：录制一条没有失败探索的黄金会话

当前 PPTX 回放忠实保留了原会话中的探索过程，包括：

- 尝试调用未注册的 `TodoWrite`。
- 尝试调用不可用的 `Glob`。
- 在文件生成前执行 `Read`。
- `Edit` 找不到字符串或没有变化。

这些过程不影响最终成功，但会让“正式演示”显得不够干净。

建议：

1. 先根据当前成功路径整理一份准确操作计划。
2. 使用同一版本 Cherry Studio、同一 Agent 配置重新跑一次。
3. 只保留真正需要的工具。
4. 录制前把需要读取的 seed 文件准备好。
5. 生成成功后再制作资产和回放剧本。
6. 连续回放三次，确认没有工具失败卡片。

公开演示版和“真实排错过程复刻版”可以保留为两个不同案例，不要混在一起。

## 3. P1：支持产物安全改名

需要区分两种“改名”：

- MCP Server 显示名或内部 UUID 变化：当前动态工具绑定已经解决。
- 用户生成后说“把文件改成 final.pptx”：当前固定剧本仍不支持。

建议增加专用 `rename_artifact` 工具，输入：

```json
{
  "from": "old-name.pptx",
  "to": "new-name.pptx",
  "artifactId": "stable-id"
}
```

安全规则：

1. 源和目标都必须位于当前 `OUTPUT_DIR`。
2. 禁止 `..`、绝对外部路径和符号链接逃逸。
3. 目标存在时默认失败，不静默覆盖。
4. 使用原子 rename。
5. 文件名变化后同步更新正文、artifact 路径、显示名和历史状态。
6. 同一 follow-up 重试必须幂等。

Provider 需要从按 turn 索引升级为简单状态机：

```text
idle → generated → renamed → reported
```

如果正式演示不需要自由改名，继续使用“演示前确定最终文件名”的简单方案更稳。

## 4. P1：处理 Topic Naming 辅助请求

当前主回放完成后，标题生成请求可能因为协议或响应形状不完全匹配而失败。

建议：

1. 为 utility 请求记录最小请求样本。
2. 根据请求用途返回兼容的非流式或流式结构。
3. utility 请求永远不能消费主剧本 turn。
4. 添加“标题生成成功但主剧本索引不变”的回归测试。
5. 如果无法稳定支持，允许配置固定标题 fallback。

验收标准：

- 主回放完成。
- 会话标题正常生成。
- Provider 仍停在正确 turn 数。
- Cherry Studio 日志没有 Topic Naming API error。

## 5. P1：自动资产生成与可复现构建

当前 PPTX 是在隔离目录里临时安装 `pptxgenjs` 后生成，再复制进 `assets/`。

建议每个由命令生成资产的案例包含：

```text
asset-build/
├── package.json
├── package-lock.json
├── generate.mjs
└── README.md
```

构建流程：

1. 固定 Node 和依赖版本。
2. 在临时目录安装依赖。
3. 运行生成器。
4. 校验页数、媒体文件和文件大小。
5. 通过 LibreOffice/Cherry Studio 打开。
6. 将最终文件复制到 `assets/`。
7. 记录 SHA-256 和构建环境。

PDF 还应：

- 使用文档示例数据。
- 运行文本脱敏扫描。
- 渲染每页 PNG 并做视觉检查。
- 检查表格裁切、字体、页眉页脚和分页。

## 6. P1：文件元数据自动写回正文

当前正文中的文件大小是人工写入的，资产重新生成后容易过期。

建议脚本支持元数据变量：

```text
{{ARTIFACT_SIZE_BYTES}}
{{ARTIFACT_SIZE_HUMAN}}
{{ARTIFACT_PAGE_COUNT}}
{{ARTIFACT_SHA256}}
```

Provider 启动时读取资产并展开，或由打包器在构建阶段写入。

这样可以避免真实文件是 `184,745 bytes`、正文仍写旧大小的问题。

## 7. P2：一键启动与健康检查

建议提供一个只读检查命令：

```text
node replay-cli.mjs doctor --script examples/ppt-demo
```

检查：

- Node 版本。
- 端口 8402。
- 剧本和资产。
- 输出目录写权限。
- Provider `/v1/models`。
- 当前工具绑定表。
- Cherry Studio 会话工作目录是否与 `OUTPUT_DIR` 一致。

再提供启动命令：

```text
node replay-cli.mjs start ppt-demo --out ~/Desktop/replay-demo-out
```

启动后打印：

- Provider URL。
- 模型 ID。
- 应发送的话术。
- 预计时长。
- 预期产物。
- 停止方式。

不要自动修改 Cherry Studio 用户配置，避免误伤真实 Provider 或 Agent。

## 8. P2：时间轴精度

当前时长来自各 block 和工具 result 的延时，总时长还会受到 SDK、IPC 和渲染影响。

建议：

1. 录制 SSE 每个 frame 的相对时间。
2. 记录工具开始、首字节、结束时间。
3. replay 使用单一绝对时间轴，不逐步累加误差。
4. 支持 `--speed 1.0`、`--speed 1.25`。
5. 连续跑五次统计 P50/P95。
6. 长案例目标误差控制在百分比范围，短案例控制在 ±2 秒。

## 9. P2：剧本 schema 与编辑器

为 `script.json` 建立 JSON Schema，编辑器至少支持：

- 剧本名称与匹配话术。
- turn 顺序。
- text/thinking/tool_use block。
- duration。
- 逻辑工具名。
- 资产路径与 artifact 描述。
- 变量预览。
- 总时长计算。

保存前执行完整预检，避免：

- tool/result 数量不一致。
- 文件名不一致。
- 忘记预生成二进制资产。
- 文本里残留真实绝对路径。
- artifact 在工作目录外。

## 10. 安全与隐私

正式化后应持续执行：

1. replay 为默认模式。
2. live/record 要求显式二次开关。
3. 上游 Key 只从环境变量或钥匙串读取。
4. 日志脱敏 Authorization、Cookie、用户消息和工具参数。
5. 分发包使用 allowlist，不做整个目录递归打包。
6. 示例服务器统一使用 RFC 5737 地址段。
7. 示例域名使用 `example.com`。
8. 对 PDF、PPTX、ZIP 内部内容也做扫描，不只扫描文件名和 JSON。
9. `.state/requests` 默认设置自动过期。
10. 发布前生成 SBOM 或最小依赖说明。

## 11. 推荐实施顺序

1. 实现 `validate` 和 allowlist `package`。
2. 重录无失败探索的 PPTX 黄金案例。
3. 修 Topic Naming utility 请求。
4. 加 artifact 元数据自动展开。
5. 实现受限 `rename_artifact` 状态机。
6. 建立 PDF/PPTX 可复现资产管线。
7. 最后再做一键启动和可视化编辑器。

完成前四项后，正式演示的现场风险会明显下降；后续三项主要提升扩展效率和非研发人员的可用性。
